# Changelog

## [Unreleased]

### Added
- The `date_info` section of the metadata sidecar has a new count, `n_contains_sample_date`: the number of points whose date is inside the time range of the image that envoi used. This is the usual case for Earth Engine datasets with `collection_date_policy: contains`, which had no count in `date_info` before.
- envoi now reports each point whose data request or read failed, for example because of a temporary Earth Engine error or a damaged block in a local raster. The run continues with the other points, and:
  - the QC table gets a column `<dataset>_error_<N>m` (`<dataset>_error_point` for point-only statistics) with the error of each failed point, and an empty value for the other points;
  - in raster runs, the tile manifest gets an `error` column with the same content;
  - each `quality` summary of the metadata sidecar, including `quality.tiles`, has `n_errors` (the number of failed points) and `ids_errors` (their IDs);
  - envoi gives one warning for each dataset and window with failed points, with the IDs of up to 10 of them, and the sidecar records it in `warnings`.

  The error columns exist only when at least one point of that dataset and window failed. `n_errors` and `ids_errors` are always present (`0` and `[]` when nothing failed). In the coverage summaries of tabular runs, a failed point is still listed in `ids_no_data`. In raster runs, `quality.tiles.n_failed` still counts every tile that was not exported, for any reason. Before, a failed point looked like a point without data. To repeat only the failed points, run `extract()` again for the IDs in `ids_errors`.
- The metadata sidecar entry of a local dataset has two new fields: `nodata`, the nodata value that envoi used for the selected bands (a number, the text `"nan"` for NaN, or `null` when there is none), and `nodata_source`, where this value came from: `"file"` (the raster file declares it), `"catalog"` (the file declares none, and the catalog entry sets `nodata`), or `null`.

### Changed
- With `input_crs` set, the reprojected `<lat>_wgs84` and `<lon>_wgs84` columns now come directly after the ID, latitude, longitude and (when present) date columns in both the statistics table and the QC table. Before, they were the last columns. The statistics table also no longer contains the `lat_original` and `lon_original` columns, which were internal copies of your latitude and longitude columns. If a script reads those two columns, read your own latitude and longitude columns instead: they hold the same input-CRS coordinates. If a script selects columns by position, select them by name.
- A column named `date` is no longer used as the sample date when your date column has another name. Before, when the input had no `eventDate` column (or no column with the name you passed as `date_column=`), envoi used a `date` column as the sample date without a notice, and renamed it to `eventDate` in the output. Now the `date` column keeps its name and values, and the run behaves as a run without dates. If your dates are in a column named `date`, pass `date_column="date"`.
- When the data request or read of every point of one dataset and window fails, the run now stops with a `RuntimeError` that names the dataset and the window and shows the error of the first point. Before, the run finished, and the outputs had empty values for every point without an error. Outputs that were written before the error, such as the files of an earlier run config in a list, stay on disk. Correct the problem (for example the network connection or your access to the dataset) and run the extraction again.
- `std` and `var` of local rasters are now population statistics: they divide by the number of valid pixels n, not n − 1, as Earth Engine's `stdDev` and `variance` do. Local and Earth Engine runs now give the same values for the same pixels. Local `std` values become smaller by the factor sqrt((n − 1)/n) and `var` values by the factor (n − 1)/n, for example about 6 % smaller `std` for a window of 9 pixels and 0.5 % for 100 pixels. A window with one valid pixel now gives `std` and `var` 0 instead of an empty value. Earth Engine values do not change.
- For the Earth Engine derived band `aspect`, the window statistics `mean`, `std`, and `var` are now circular statistics, because aspect is a direction. For example, the mean of 350° and 10° is now 0° (north), not 180° (south). `std` is the circular standard deviation in degrees, and `var` is its square. Pixels with slope 0 are not used for these three statistics, because Earth Engine gives flat pixels the aspect 0 (north); a window with only flat pixels gives empty values. The values change most for slopes that face north, where the old values could point in the opposite direction. Column names do not change, and the other statistics of aspect (`median`, `min`, `max`, quantiles, `sum`, `mode`, `point`) are still linear values from 0 to 360. See [Circular aspect statistics](docs/advanced_usage.md#circular-aspect-statistics).
- For Earth Engine collections with `collection_date_policy` `nearest` (the default) or `contains`, a point where the collection has no image at all (on any date, for example an ocean point of `aef_satellite_embeddings`) is now a point without data, as such points already were with `collection_date_policy: mosaic`: its statistics are empty, except `count` and the per-class columns of `class_count` and `class_fraction`, which are `0`; `in_extent` is `False`; and in raster runs it gets a tile in which every pixel is masked. Before, the Earth Engine request for that point failed: the point looked like a point without data, and in raster runs no tile was written (`exported` was `False` in the tile manifest). A point that has images, but none on the selected dates, gets an image of its own near its date (see "Fixed"). A point that has images, but none that envoi can select (none within 366 days of its date, or none in its UTM zone for datasets with `use_utm_zone`), is a failed point (see "Added").
- Raster tiles of Earth Engine and local datasets now follow one rule for their size and position, the rule that the README states. A tile has n × n pixels, where n is `window_size_m` divided by the pixel size (`resample_m`, or the native pixel size of an Earth Engine dataset without `resample_m`), rounded to the nearest whole number with ties rounded up, and at least 1. Tile corners lie on multiples of the pixel size in the point's UTM zone. The width and the height of a tile can change by one pixel, up or down:
  - Earth Engine tiles now have an odd size when n is odd. For example, a 200 m window at 30 m gives 7 × 7 pixels instead of 6 × 6. A window smaller than 1.5 pixels now gives a 1 × 1 tile instead of 2 × 2.
  - Earth Engine tiles at a native pixel size that is not a whole number of metres no longer get an extra row or column at some points. For example, a 200 m window of `dem_copernicus_glo30` (30.92 m pixels) now gives 6 × 6 pixels at every point. Before, it gave 7 × 7 pixels, or 7 rows of 6 pixels, depending on the point. The pixel values do not change.
  - Tiles with an odd size are now centred on the pixel that contains the point. Local tiles with an odd size can move by one pixel for this reason. A tie now always rounds up, so a few local tile sizes change: for example, a window of 2.5 pixels now gives 3 × 3 pixels instead of 2 × 2.
  - Local tiles without `resample_m` do not change.

  If a script or a model expects a fixed tile size, check the size of new tiles.
- `native_spatial_resolution_m` of local datasets in the metadata sidecar, and the `resolution_m` that envoi fills in for local rasters, are now in metres also for rasters whose CRS is in degrees or feet. Before, they were in the units of the CRS: for example, 0.001 for a raster with pixels of 0.001° (now 111.32), or 100 for pixels of 100 US survey feet (now about 30.48). For a CRS in degrees, envoi uses 111 319.49 m per degree, the length of one degree at the equator, as Earth Engine does. Away from the equator, the value is therefore larger than the east-west width of a pixel on the ground. For a CRS without a unit of length, both values are now empty (`null`).
- In the metadata sidecar of a raster run with `resample_m`, `tile_crs` of a local dataset is now the list of the UTM zones of the points, for example `["EPSG:32633", "EPSG:32634"]`, as for Earth Engine datasets. These tiles are in the UTM zone of each point. Before, `tile_crs` was the CRS of the raster file, which these tiles do not use. Without `resample_m`, local tiles keep the CRS of the raster file, and `tile_crs` is still that CRS as text. If a script reads `tile_crs` as text, change it to also accept a list.
- envoi now reads only these date values, and raises a `ValueError` for every other value before any extraction: text dates `YYYY`, `YYYY-MM`, `YYYY-MM-DD` (also with a one-digit month or day, such as `2021-6-5`), `YYYYMMDD`, and `YYYY/MM/DD`; each of these forms except `YYYY/MM/DD` also with a time of day after `T` or one space and a time zone (such as `2021-06-15T08:00Z`); ISO 8601 intervals (`start/end`); date and datetime values; and whole numbers with four digits (years, such as `2021`) or eight digits (`YYYYMMDD`, such as `20210615`, which a CSV reader stores as a number). The error names your date column and lists up to 10 of the values, for example `05-06-2021`, `05.06.2021`, `June 5, 2021`, or a date that does not exist, such as `2021-02-30`. Before, envoi let pandas guess the form of such values, and pandas read the first number as the month: `05-06-2021` and `05.06.2021` became May 6, 2021, without a warning, also when the data meant June 5. If your dates have another form, convert them before you call `extract()`, for example with `pd.to_datetime(df["eventDate"], format="%d.%m.%Y")` when you know that the day comes first (envoi reads datetime columns). Other numbers raise, for example `2021.5`, `202106`, or `15062021` (as `YYYYMMDD`, its month would be 20). Some forms work better now: `YYYYMMDD` dates, as text or as numbers, no longer give a wrong warning that the date is incomplete, and a column of years or of `YYYYMMDD` dates with a missing value (decimal numbers such as `2021.0` or `20210615.0`) no longer stops the run. A time of day after a space (`2021-06-15 08:00`) now also gives the time-of-day warning. See [Date-aware extraction](docs/advanced_usage.md#date-aware-extraction).
- For Earth Engine datasets, every band list in `datasets` (a per-call band override) now gives columns named after the bands, also a list of one band, as the documentation says and as local datasets already did. For example, `{"dem_copernicus_glo30": ["DEM"]}` now gives `dem_copernicus_glo30_DEM_mean_200m` instead of `dem_copernicus_glo30_mean_200m`, and `{"sr_landsat_annual": ["red"]}` gives `sr_landsat_annual_red_mean_200m` instead of `sr_landsat_annual_mean_200m`. Point columns (`<dataset>_<band>_point`) and the columns of count-only runs follow the same rule. A plain dataset name (the catalog's default bands) keeps its column names. A band list of only derived bands now replaces the catalog's bands: `{"dem_copernicus_glo30": ["aspect"]}` gives only the aspect columns, such as `dem_copernicus_glo30_aspect_mean_200m`. Before, it also gave the columns of the catalog's band `DEM`, and the metadata sidecar recorded `bands: ["DEM"]` for it; it now records `bands: []` and `derived_bands: ["aspect"]`. If a script reads such columns, change the names in the script.
- For Earth Engine collections with `collection_date_policy` `nearest` (the default) or `contains`, the QC columns `<dataset>_image_time_start_<N>m` and `<dataset>_image_time_end_<N>m`, and `image_date_ranges_used` in the `date_info` section of the metadata sidecar, now name the image that each point actually used (see "Fixed"). Before, they named the image that envoi selected for the batch, also when the point used another image or none. `<dataset>_date_clamped_<N>m` and `<dataset>_date_source_<N>m` do not change. A point where the collection has no image at all now has empty date columns, and `date_info` does not count it. `image_time_end` is empty when the image has no end time. In raster runs of these collections, envoi sends one more small request for each tile to read the dates of its image. When this request fails, the tile is a failed tile (see "Added"), and a tile with the same name from an earlier run is removed.

### Fixed
- Per-class columns of categorical datasets with named bands, such as `lulc_naturallands_2020_classification_class_10_count_200m`, are now `0` (count) or `0.0` (fraction) for points whose window did not contain that class, as other class columns already were. Before, these cells were empty, so an absent class looked like missing data. This affected Earth Engine runs that extract more than one band of a categorical dataset; single-band runs and local rasters were already correct.
- A missing, non-numeric, or infinite latitude or longitude now stops the run before any extraction, with a `ValueError` that names your coordinate columns and lists the IDs of the affected rows. Before, text gave an unclear `TypeError`, infinity gave an error that said the coordinates were not in WGS84, and a missing value failed later without naming the row, or gave empty statistics. Coordinates stored as text that holds a number, such as `"59.85"`, are now accepted.
- An extra input column named `id`, `lat`, `lon`, `date`, `lat_original`, or `lon_original` no longer breaks the run. For example, Darwin Core files often have an `id` column next to `occurrenceID`. Before, an extra `id` column gave two `occurrenceID` columns in the statistics table and an unclear error in raster mode, and the other names gave unclear errors. Now such a column keeps its name and values in the statistics table, and envoi does not use it. This also fixes web app uploads that have such a column.
- Two run configs in one list with the same `batch_id` now raise a `ValueError` before any output is written. This includes `batch_id` values that differ only in letter case, such as `Terrain` and `terrain`, because Windows and macOS treat such file and folder names as the same name. It also includes a run config without `batch_id`, which gets the name `output<N>` (N is its position in the list, starting at 1). A tabular `batch_id` such as `terrain_qc` also raises when another tabular run config has the `batch_id` `terrain`, because envoi writes the QC table of `terrain` to the file `terrain_qc.csv` (or `.parquet`). Before, the later output overwrote the files of the earlier one, and the returned dict held only one of them. envoi now also checks every run config in the list before the first one runs, so an invalid setting in a later run config stops the call before any output is written or any Earth Engine quota is used.
- A run config that lists the same dataset twice in `datasets`, for example `["dem_copernicus_glo30", {"dem_copernicus_glo30": ["slope"]}]`, now raises a `ValueError` before any output is written. List the dataset once, with all the bands you need, for example `{"dem_copernicus_glo30": ["DEM", "slope"]}`. In raster runs, two datasets whose names differ only in letter case, such as `dem` and `DEM`, also raise, because Windows and macOS treat their tile folders as one folder. Before, the output of the second entry overwrote the output of the first.
- `resample_m` and `min_coverage_pct` must be finite numbers. Text (such as `"30"`), `true`/`false`, NaN, and infinity now raise a `ValueError` that names the output. `min_coverage_pct: null` also raises; `resample_m: null` still means no resampling. Before, some of these values gave an unclear `TypeError`, and others were accepted with a wrong result: `true` was read as `1`, and `min_coverage_pct: nan` never flagged low coverage. NumPy numbers such as `np.float32(30)` are accepted, and the metadata sidecar records them as plain numbers.
- Dates written `YYYY/MM/DD`, such as `2021/06/15`, are now read as that date. Before, envoi kept only the year and used January 1 of that year, with a warning such as `Date '2021' interpreted as 2021-01-01`.
- Other date values with `/`, such as `15/06/2021`, `06/15/2021`, `06/2021`, or `2021/6/5`, now stop the run before any extraction, with a `ValueError` that names your date column and lists the values. Before, envoi kept only the part before the first `/`, which gave a wrong date (for example, `2021/6/5` became January 1, 2021) or an unclear error. Write these dates as `YYYY-MM-DD`. A value with exactly one `/` whose start is an ISO 8601 date or date-time, such as `2021-06-15/2021-06-20`, is still read as an interval (`start/end`), and envoi uses its start day.
- For Earth Engine datasets with `collection_date_policy: contains`, a sample date on the start of the first image, or inside the time range of the last image, is no longer marked as clamped. Before, the QC columns `<dataset>_date_clamped_<N>m` and `<dataset>_date_source_<N>m` showed `True` and `clamped_to_nearest` for these dates, and the sidecar `date_info` counted them as clamped, although envoi used the correct image. The statistics do not change. A date is now clamped only when it is before the start day of the first image, or on or after the end of the last image's time range. This time range always includes the whole start day of the last image.
- The `date_info` section of the metadata sidecar is no longer missing when the request for the first point of an Earth Engine dataset failed. Before, envoi looked for date information only in the first point.
- Custom Earth Engine datasets with `collection_date_policy: contains` whose images start and end on the same day (for example, images whose `system:time_end` is equal to `system:time_start`) now get statistics and tiles. Before, envoi searched for such an image in an empty date range, so the statistics were empty and no tile was exported. The built-in `contains` datasets were not affected, because their images cover 8 days or more.
- Earth Engine collections in which two images have the same start time and different end times no longer break date selection. envoi now keeps one time range per start time, with the latest end time. Before, with `collection_date_policy: nearest` (the default) and a date column, every point of such a dataset failed: the statistics were empty, and raster runs stopped with an unclear error.
- A tile download from Earth Engine that fails part way no longer leaves an incomplete GeoTIFF next to the valid tiles. envoi now writes each tile to a temporary file and gives it the tile's name only when the download is complete. When a download fails, envoi also removes a tile with the same name from an earlier run, so that the folder matches the tile manifest. Also, an HTTP status other than 200, 429, or 5xx (for example 400) is no longer retried: the tile fails at once, and its error now includes Earth Engine's error message.
- Earth Engine raster runs whose tiles are too large for Earth Engine's download limit (about 32 MB for each tile) now stop with a `ValueError` before any tile is downloaded. The error tells you to reduce `window_size_m`, increase `resample_m`, or select fewer bands. Before, every tile failed with a warning, and the run ended without tiles and without an error.
- When Earth Engine cannot return the image dates of a collection (for example, because of a network error or a timeout), the run now stops with a `RuntimeError` that names the collection. Run the extraction again. Before, envoi logged a warning and continued without the image dates, so it could not select the image for each sample date: points without a date got a mosaic of the most recent images, points with a date got an image from within one day of the sample date (or empty statistics when there was none), and the outputs did not show this.
- A temporary error in the request for the band names of an Earth Engine dataset no longer makes every later point of that dataset fail. This request is made only for datasets whose bands are not set in the catalog or the run config. Before, envoi kept the placeholder band name `value` after one failed request, and every later point of the dataset got empty statistics. Now envoi asks again for the next point. In raster runs, envoi needs the band count before the first download, so a band-name request that fails twice now stops the run.
- envoi no longer replaces an Earth Engine session that is already initialized, for example a session that you started with `ee.Initialize()` or `envoi.init_gee()`. Before, envoi sent a test request when it set up the first Earth Engine dataset. When that request failed, for example because of a temporary network error, envoi initialized Earth Engine again with the credentials file that `init_gee()` finds, which could replace your credentials and Cloud project, or stop with "credentials not found" and hide the real error. Now envoi initializes Earth Engine only when it is not initialized, and sends no test request.
- A read error in a local raster, for example a damaged block in the file, no longer stops the whole run. The point is reported as a failed point (see "Added"), and the other points get their values. A failed pixel read for the `point` statistic no longer looks like a point outside the raster. When a point needs both a window read and a pixel read (window statistics together with `point`), an error in either read now makes every statistic of that point empty.
- In Earth Engine runs that extract more than one band, a point whose request failed no longer adds statistic columns without a band name, such as `<dataset>_mean_<N>m`, which were empty for every point. The failed point now has empty values in the usual `<dataset>_<band>_<statistic>_<N>m` columns. Also, the per-class columns (`class_count`, `class_fraction`) of a failed point are now empty instead of `0`, because the classes at that point are unknown.
- For Earth Engine datasets, `in_extent` in the QC table is now `False` for a window without valid pixels also when the statistics include `sum` or `count`. Earth Engine gives `0` for these two statistics on such a window, and envoi read the `0` as data, so `in_extent` was `True` with `n_pixels` `0`. `in_extent` now comes from the pixel counts: it is `True` when at least one band has a valid pixel in the window. `count` stays `0` for such a window, and `sum` is now empty (see the entry about `sum` of a window without valid pixels).
- Earth Engine runs whose only statistic is `count` now give correct results. With one band, the count was correct, but the QC table showed `n_pixels` 0, `coverage_pct` 0, and `had_nodata` `True` for every point, and envoi warned about low coverage for every point. With more than one band (for example `{"dem_copernicus_glo30": ["DEM", "slope"]}`), the statistics table had no count columns, and the QC table showed every point as outside the extent. Now the run gives one `<dataset>_<band>_count_<N>m` column for each band, and the QC values come from the counts (with several bands, from the smallest count). `in_extent` is `True` when at least one count is above 0. Note that Earth Engine counts only whole pixels when `count` is the only statistic, but also pixels partly inside the window when there are other statistics. A count-only run can therefore show a `coverage_pct` a few percent below 100 (and `had_nodata` `True`) for a window without missing data.
- A local `point` value from a pixel that is NaN or infinite is now empty, also when the raster declares no nodata value. The QC columns now show such a point as a point without data (`in_extent` `False`, `n_pixels` 0, `had_nodata` `True`), as for a nodata pixel. Before, the value was NaN (empty in CSV files) or infinite (`inf`), and the QC columns showed the point as a valid pixel inside the extent.
- Window statistics of a local raster no longer have empty values when the window is smaller than one pixel of the raster, for example `window_size_m: 50` on a raster with 100 m pixels. Before, such a window often contained no pixel centre, so the statistics were empty and the QC columns showed no pixels. Now envoi widens the window to two pixels, as it already did for Earth Engine datasets. The column names and the metadata keep the window you requested, and the QC coverage describes the widened window. envoi uses the pixel size in metres (see "Changed"); a raster whose CRS has no unit of length is not widened.
- The local `point` statistic no longer uses the `*` operator of `affine` transforms, which `affine` 3 deprecates. With `affine` 3, this gave a `PendingDeprecationWarning`. The values do not change.
- A catalog entry with an unknown `data_source`, for example `gee` instead of `earth_engine`, now stops with a `CatalogError` (a `ValueError`) when you register it with `update_catalog()`, from a dict or from a YAML file. The error names the dataset and the value, and lists the valid values (`earth_engine`, `local`). Before, envoi accepted the entry, and `extract()` raised a `KeyError` only when it reached that dataset, possibly after other datasets of the run had used Earth Engine quota.
- Raster tiles of points whose IDs differ only in letter case, such as `Site1` and `site1`, no longer overwrite each other on Windows and macOS. These systems treat `Site1-<dataset>.tif` and `site1-<dataset>.tif` as one file, so one of the two tiles was lost, although the tile manifest listed both as exported. Such IDs now get the short hash suffix that envoi already adds to IDs with characters that are not allowed in file names, for example `Site1-d235a19f-<dataset>.tif` and `site1-8e62d73f-<dataset>.tif`. This applies to Earth Engine and local datasets. The names of all other tiles do not change. The tile manifest (`tiles_manifest.csv`) gives the file name of each ID.
- A `nodata` value in the catalog entry of a local raster is now used when the raster file declares no nodata value. Before, envoi ignored it, so pixels with this value counted as data: in the `point` statistic, in the window statistics (for example, `-9999` pixels made the `mean` far too low), and in the tiles. Now these pixels are missing data in every selected band, in statistics and tiles, and the tiles declare this value as their nodata value. `nodata` must be one number that fits the data type of the bands, for example a whole number from 0 to 255 for `uint8` (`-9999.0` counts as the whole number `-9999`). A list of values, or a value that the bands cannot store, now stops the run with a `ValueError`. The statistics of such rasters change. See [Custom datasets](docs/advanced_usage.md#custom-datasets).
- A `crs` in the catalog entry of a local raster is now used when the raster file has no CRS. Before, envoi ignored it, and the run stopped with an unclear `CRSError` ("CRS is invalid: None"). A file without a CRS and without a catalog `crs` now stops with a `ValueError` that tells you to add `crs` to the catalog entry.
- A catalog `nodata` or `crs` of a local raster that differs from the value in the raster file now stops the run with a `ValueError` that names both values. envoi uses the values of the file, as before, but did not tell you about the difference. The values that envoi fills in when you register a catalog YAML file always agree with the file. envoi checks every local dataset of an `extract()` call, with the bands that each run config selects, before it reads any data. A missing file, and a band number that the file does not have (which gave an unclear `IndexError` before), also stop the call at this point, before any output is written.
- Your own extra columns in the input table, for example a column of measurements, are no longer rounded to 5 decimals in the statistics table. Before, envoi rounded every column except the ID, coordinate, and date columns. Only the statistic columns that envoi adds are rounded (`stats_output_decimals` in `defaults.yml`).
- The web app now rejects a CSV file with an infinite latitude or longitude (for example the text `inf`) when you upload it, with a message like the one for missing coordinates. Before, the upload was accepted, and the error came only when the extraction started.
- Window statistics of a local raster with several integer bands (for example a `uint16` multispectral GeoTIFF) no longer stop with `TypeError: Cannot convert fill_value nan`. Single-band and floating-point rasters were not affected.
- An input column with the name of a column that the same `extract()` call adds to its output tables, for example `dem_copernicus_glo30_mean_200m` in an input table that is the output of an earlier envoi run, now stops the run with a `ValueError` before any extraction. This includes the statistic and QC columns of each dataset and window of a tabular run config (also the `point` columns), and `<latitude column>_wgs84` and `<longitude column>_wgs84` when envoi reprojects the coordinates from `input_crs`. The message names the columns. Remove or rename them before you call `extract()`. Columns of other datasets or other windows are not affected, and raster runs add no columns, so they do not check this. Before, envoi replaced the values of such a statistic column without notice, a column with the name of a QC column was removed from the statistics table and was twice in the QC table, and a `_wgs84` column stopped the run with an unclear error after the extraction.
- For Earth Engine datasets, `sum` is now empty for a band whose window has no valid pixel, as for local datasets. Before, Earth Engine gave `0`, which looked like the sum of pixels with the value 0. `count` stays `0` for such a window, as do the per-class columns of `class_count` and `class_fraction`. This also applies to a point where the collection has no image at all (see "Changed").
- The `date_info` section of the metadata sidecar of a raster run no longer counts failed tiles. Before, a tile whose request or download failed was counted in `date_info` (for example in `n_nearest_to_sample`), and its image could be listed in `image_date_ranges_used`, although envoi wrote no tile for it.
- Earth Engine collections in which some images have no `system:time_start` or no `system:time_end` no longer get wrong image time ranges. envoi now reads the start and end time of each image together. Before, envoi read all start times and all end times as two separate lists, and Earth Engine leaves out the missing values. When one image had no start time and another image had no end time, the two lists had the same length, and envoi paired the start of one image with the end of another image. Now an image without a start time is not used for the date selection, and when an image with a start time has no end time, envoi uses only the start times, as for a collection without end times.
- For Earth Engine datasets with `collection_date_policy: contains`, envoi now compares whole days (in UTC) when it selects the image for a sample date. An image that starts later on the sample day, for example at 10:00, now contains that day: envoi selects it, and the date is not marked as clamped. Before, envoi compared 00:00 of the sample day with the start time, so it selected the image before it, or marked the date as clamped when the image was the first image. Also, when the collection has no end times, a date after the start day of the last image is now clamped, also when this image starts later in its day. The built-in `contains` datasets were not affected, because their images start at 00:00.
- For an Earth Engine collection with selected bands, the masked image that envoi uses for a point where the collection has no image now has these bands: it is the first image of the collection that has all of them. Before, it was the first image of the collection. When the images of a collection have different bands, that image could miss a selected band, and the point failed with an error that the band was not found.
- Earth Engine collections whose images have different dates at different places, for example the tiles of Sentinel-2 (`COPERNICUS/S2_SR_HARMONIZED`), now give each point an image that covers it. envoi selects the image date for the batch, and a point without an image on that date now gets an image of its own near its date, which Earth Engine selects in the point's own request, first within 32 days, then within 366 days. With `collection_date_policy: nearest`, this is the image with the fewest whole days between its start and the date (the earlier image when two are equally near). With `contains`, it is the image that contains the date, else the latest image that starts before it, else the earliest image after it. Before, such a point was a failed point with empty statistics: for example, Sentinel-2 points at Uppsala and Göteborg on 2021-06-16, in one run, have no image on a common day, and the Uppsala point failed. Also with `contains`, a point no longer gets an image that starts after its date only because another point of the batch has a longer image. This also applies to runs without a date column. The search takes time only for these points: in live checks with Sentinel-2, their requests took about 1 s longer, and up to about 3 s longer when the search needs the 366-day window. Points that have an image on the selected date keep their image.

### Documentation
- New section "Known limitations" in `docs/advanced_usage.md`: how `n_pixels` and `coverage_pct` differ between adapters, `in_extent` for windows without valid pixels, class columns after failed points, tiles from earlier runs, local paths in the metadata sidecar, and `date_info` in runs with several windows.
- The README explains when a tile name gets a hash suffix, and that `tiles_manifest.csv` maps each ID to its tile.

## [0.2.2] — 2026-08-28

### Added
- `catalog_markdown()` renders the dataset catalog as a formatted Markdown document — readable output for notebooks and docs instead of raw dicts.
- Catalog entries accept two new optional keys, both surfaced by `list_datasets("info")`: `display_name`, a human-readable label following the dataset's title in the Earth Engine catalog (e.g. `dem_copernicus_glo30` → "Copernicus DEM GLO-30"), and `category`, the theme the dataset is grouped under. Every built-in dataset now sets both. `display_name` falls back to the dataset key when an entry omits it, so it is always safe to display.
- New `dataset_spec` option `collection_date_policy: mosaic`, for Earth Engine collections that tile space rather than time — one static product cut into geographic tiles, where each image's timestamp records when that tile was acquired. Dates are ignored and the tiles covering each point are mosaicked. Without it, such timestamps are read as a time axis and "most recent image" selects a tile elsewhere on the planet, nulling every statistic.

### Changed
- `dem_copernicus_glo30` now points at `COPERNICUS/DEM/GLO30_2024_1`. Earth Engine has deprecated the original `COPERNICUS/DEM/GLO30`, and using it printed a deprecation warning on every run. Elevation values are unchanged (verified identical to 5 decimal places on sample points); the new release carries real per-tile acquisition dates, so the entry declares `collection_date_policy: mosaic`. **Derived `slope` and `aspect` values shift slightly** (up to ~6° of aspect on tested points) because they are now computed across a mosaic of neighbouring tiles instead of a single tile, which removes tile-edge artefacts. All other datasets were audited against Earth Engine's deprecation registry and are current.

- Raster output now writes a `tiles_manifest.csv` into each dataset's tile folder, mapping every input row to the tile file it produced (`<your id column>`, `tile_filename`, `exported`). Join it onto your input table to find a point's tile, including for points whose tile failed to export. Multi-window runs write one suffixed manifest per window (`tiles_manifest-200m.csv`).

### Fixed
- **Tile filenames are now portable across Windows, macOS and Linux.** Tile names are built from your ID column, which was previously interpolated into the path unchanged. URL-style occurrenceIDs (`http://arctos.database.museum/guid/MSB:Mamm:1`) contain `/`, which scattered tiles into nested directories on the Earth Engine path and raised an error on the local-raster path; `urn:catalog:...` IDs contain `:`, which is illegal on Windows. IDs are now reduced to `[A-Za-z0-9._-]`, with a short hash appended when a rewrite was needed so two IDs can never collide. **IDs that were already portable are untouched, so existing tile filenames are unchanged.**
- Raster mode now rejects blank and duplicated sample IDs up front, with a message naming the offending rows. Previously duplicated IDs silently overwrote each other's tiles and blank IDs produced a `nan-<dataset>.tif`, so a run could return fewer tiles than points with no error. The web app applies the same check when a CSV is uploaded. Tabular mode is unaffected — duplicates are harmless in a column.
- `batch_id` values and `update_catalog()` dataset names are validated as path components, since both become folder names. An unusable one (`my/batch`, `..`, a name with spaces) now raises instead of producing a broken or misplaced output folder.

### Documentation
- New generated dataset reference at `docs/datasets.md`: every built-in dataset grouped by theme, with a summary table plus resolution, temporal coverage, bands, licence, citation, and links per entry. Regenerate it with `python scripts/generate_dataset_docs.py` after editing `ee_catalog.yml`; a test fails if the committed file drifts out of sync.
